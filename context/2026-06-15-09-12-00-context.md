# Round 28 — Reuso de email após soft-delete (LGPD-compliant)

## Sintoma reportado

User (Lucas) tentou se cadastrar em prod com `k3ntluk@gmail.com` e
recebeu 409 CONFLICT. Tentou 3 vezes (08:41:27/42/57), todas 409.
Contornou criando `k3ntluk2@gmail.com` às 08:54:01 (sucesso 201).

Critical-flows estava verde (20/20) — não pegou o bug porque cada run usa
sufixo único (`critical-flows-{ts}-{pid}@test.viralefy.com`).

## Root cause

`UserRepo.GetByEmail` em ambos `viralefy_auth` e `viralefy_core` retornava
users soft-deletados:

```go
// ANTES
SELECT ... FROM users WHERE email=$1
```

Em `RegisterUser` (auth e core), o conflict check disparava antes do
INSERT:

```go
if existing, _ := s.users.GetByEmail(ctx, email); existing != nil {
    return nil, domain.ErrConflict
}
```

`k3ntluk@gmail.com` foi soft-deletado em 2026-06-12 14:45 (cleanup
de QA). Como GetByEmail não filtrava `deleted_at IS NULL`, retornava
o registro, e o check disparava 409.

Bug paralelo: UNIQUE constraint `users_email_key` cobria todos os
emails (inclusive soft-deletados). Mesmo com fix no GetByEmail, o
INSERT bateria duplicate key.

## Mudanças

### `viralefy_core/internal/infrastructure/persistence/postgres/migrations/047_users_email_unique_partial.{up,down}.sql`

- Drop `users_email_key` (UNIQUE constraint total)
- Create `users_email_active_key` UNIQUE WHERE `deleted_at IS NULL`

Down restaura UNIQUE total. Se houver duplicatas (active + soft-deleted),
rollback falha — operador renomeia email do soft-deletado manualmente.

### `viralefy_auth/internal/infrastructure/persistence/postgres/user_repo.go`

`GetByEmail` agora adiciona `AND deleted_at IS NULL`. Doc atualizada
referenciando a migration 047 e LGPD Art. 18 IV.

### `viralefy_core/internal/infrastructure/persistence/postgres/user_repo.go`

Mesma mudança no GetByEmail.

### `viralefy_ops/bin/viralefy-critical-flows`

Novo flow `flow_db_invariant_softdelete_reuse`:
1. `users_email_active_key` parcial presente
2. `users_email_key` UNIQUE total ausente

Se rollback parcial deixar ambos coexistindo, o flow detecta. Roda só
se psql estiver disponível (servidor de prod). Pula em local.

## Callers de GetByEmail revisados

Todos se beneficiam do filtro:

| Caller | Antes | Depois |
|---|---|---|
| `auth.LoginUser` | tinha `DeletedAt == nil` defensivo | filtro no SQL (redundância removida) |
| `auth.RegisterUser` | 409 espúrio em email soft-deleted | 201 normal |
| `auth.RequestPasswordReset` | enviava reset pra soft-deleted | no-op silencioso (anti-enum mantido) |
| `core.UserAuthService.Register` | 409 espúrio | 201 normal |
| `core.UserAuthService.Login` | sem check, login impossível por bcrypt mismatch | filtro no SQL |
| `core.UserAuthService.EnsureShadowAccount` | reusava soft-deleted (errado) | cria novo |
| `core.CheckoutService` autocadastro | reusava soft-deleted (errado) | cria novo |
